# [LS-05][高] UDP 转发会话串扰，数据包进错内网目标

严重程度：高

建议标签：`bug`

相关报告：[LinkStar 审查报告](../LinkStar-audit-report.md) 第 LS-05 节。

## 现象

两个 UDP 洞如果看到同一个客户端源地址，后一个洞的载荷会被写进前一个洞已经拨出的内网连接。第二个内网服务收不到这个包。

## 定位

- `modules/stun/forward.go`：第 117 行 `var udpSessions sync.Map`，注释写明键是 `remoteAddr.String()`；`ForwardUDP` 第 120–154 行
- `modules/stun/stun.go`：第 218 行，每个 UDP 洞都调用这个包级函数

## 根因

会话键只有客户端地址，没有本地监听端口，也没有目标地址。`Load` 命中后直接 `Write` 到已有 `net.Conn`，不再看这次的 `targetAddr`。

## 稳定复现步骤

1. 在 `127.0.0.1` 上开两个 UDP 接收端 A、B，再开一个本地 `UDPConn` 当作洞口。
2. 用同一个伪造远端 `203.0.113.9:40000` 调用  
   `ForwardUDP(local, remote, []byte("to-A"), A 的地址)`，稍等，再  
   `ForwardUDP(local, remote, []byte("to-B"), B 的地址)`。
3. 看两个接收端各自收到的字节。

## 预期 vs 实际

预期：`to-B` 只出现在 B。

实际：`serverA got=["to-A" "to-B"]`，`serverB got=[]`。

## 建议修复方向

键改成「本地端口 + 客户端地址」，或者每个服务一张表。已有会话的目标地址变了就关掉旧连接再拨。`Write` 的错误要处理，避免死连接一直留到 30 秒读超时。

## 证据摘要

审查时用临时测试打出上面的 `got` 结果后已删除该测试，业务代码未改。复现只依赖 `ForwardUDP` 的现有签名，不需要公网。
