# [LS-03][高] JWT 密钥以 0644 落盘，可伪造管理员 token

严重程度：高

建议标签：`bug`

相关报告：[LinkStar 审查报告](../LinkStar-audit-report.md) 第 LS-03 节。

## 现象

第一次启动就生成 `jwtSecret`，和密码哈希一起写入 `config/authConfig.json`。目录 `0755`、文件 `0644`（umask 022）。同机其他用户读到文件后可以伪造 `sub=admin` 的 HS256 token，不必知道密码。设置密码不会轮换这个密钥，只有修改密码才会。

DNS 服务商凭证在同样权限的 `config/ddnsConfig.json` 里。证书私钥是 `0600`，配置文件没有同样收紧。

## 定位

- `utils/utilsFile/utils_json.go`：`WriteJsonFile` 第 73–82 行，`os.WriteFile(..., 0644)`
- `modules/auth/auth_config.go`：`createConfig` 第 40–55 行（`MkdirAll("config", 0755)` 并立刻写入 `JwtSecret`）；`randomSecret` 第 69–74 行，`crypto/rand` 失败时退回 `time.Now()` 的十六进制
- `modules/auth/store.go`：`ValidateToken` 第 133–141 行，只拿当前 `JwtSecret` 验签
- `utils/jwt/enter.go`：`ParseToken` 第 33–40 行，算法限定 HS256，不看别的身份条件

## 根因

密钥在「尚未设置密码」时就已经落在世界可读的 JSON 里。`Setup` 不调用 `randomSecret()`。校验只看签名和过期时间，所以抄到密钥就等于管理员。

## 稳定复现步骤

1. 启动程序，等 `config/authConfig.json` 出现。`stat -c '%a' config/authConfig.json` 得到 `644`。
2. 用文件里的 `jwtSecret` 做 HMAC-SHA256。header 为 `{"alg":"HS256","typ":"JWT"}`，payload 为 `{"sub":"admin","iat":现在,"exp":一小时后}`。
3. `curl -H "Authorization: Bearer <伪造 token>" http://127.0.0.1:3333/api/stun/config`。
4. 也可以在设置密码之前把密钥抄走。`Setup` 不轮换密钥，设置完成之后同一把密钥仍然有效，直到有人修改密码。

## 预期 vs 实际

预期：密钥和密码哈希只有运行用户可读；设置密码时轮换密钥，使事先抄走的密钥失效。

实际：审查中伪造 token 访问受保护的 `/api/stun/config`，HTTP 200，正文是 STUN 配置 JSON。`authConfig.json` 的权限是 `644`。密钥和 token 没有写入本仓库。

## 建议修复方向

`config/` 用 `0700`，含密钥的 JSON 用 `0600`。已经存在的 `0644` 文件在读取时收紧权限。`Setup` 成功时换一把 `randomSecret()`。`crypto/rand` 失败时让启动失败，不要用时间戳当密钥。

## 证据摘要

第一次启动后 `find` 显示 `644 config/authConfig.json`，而 `data/cert/1/privkey.pem` 是 `600`。第二次启动在设置密码之后，用文件中的密钥伪造的 token 拿到了 `/api/stun/config` 的 200。
