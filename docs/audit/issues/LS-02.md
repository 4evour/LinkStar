# [LS-02][高] 未设密码时任意主机可抢走管理权

严重程度：高

建议标签：`bug`

相关报告：[LinkStar 审查报告](../LinkStar-audit-report.md) 第 LS-02 节。

## 现象

首次启动、`initialized` 仍为 false 时，不带任何凭证调用 `POST /api/auth/setup` 就会成为唯一管理员，并拿到可用 JWT。程序听在所有网卡的 3333 端口上。README 只写了「第一次进管理后台会引导设置密码」，没有写同网段其他人可以抢先。

## 定位

- `routers/enter.go`：`Run`，第 107 行 `Addr: "0.0.0.0:3333"`
- `routers/auth_routers.go`：`AuthRouters`，第 18–19 行 `POST auth/setup` 挂在公开组
- `modules/auth/store.go`：`AuthRuntime.Setup`，第 68–97 行。未初始化时只检查密码长度并写入哈希，不检查来源

## 根因

监听 `0.0.0.0`，设置密码的接口在密码尚未存在时完全公开，没有本机限制，也没有一次性引导令牌。谁先 POST 谁就成为管理员。

## 稳定复现步骤

1. 空目录启动 `./linkstar`。
2. `curl -s http://127.0.0.1:3333/api/auth/status`  
   实测返回 `{"code":0,"data":{"authed":false,"initialized":false},"msg":"成功"}`。
3. 还没打开管理页时执行  
   `curl -s -H 'Content-Type: application/json' -d '{"password":"<至少 8 位>"}' http://<主机>:3333/api/auth/setup`。
4. 响应 `code` 为 0，且 `data.token` 非空。再次 `GET /api/auth/status`，`initialized` 变为 `true`。
5. 真正的使用者再打开管理页，只能用这次设下的密码登录。要重来得删 `config/authConfig.json`。

审查时这一步是在本机对 `127.0.0.1:3333` 做的。绑定地址是 `0.0.0.0`，同一请求从其他能访问该端口的主机发出结果相同。

## 预期 vs 实际

预期：设置密码只接受来自本机的连接，或要求用户在启动日志里抄一个一次性口令。

实际：未带凭证的 POST 直接返回 JWT，状态变为已初始化。不带 token 再访问 `/api/stun/config` 仍是 401，说明被抢走的是「谁来设第一把密码」，不是未初始化时管理接口已经放开。

## 建议修复方向

`Setup` 只允许 `127.0.0.1` / `::1`，或启动时在日志打出一次性 setup token，请求里必须带上。路线图里的「管理端口可配置」不能代替这个初始化窗口的来源限制。

## 证据摘要

第二次启动（`run-logs/run2.stderr.txt` 对应的进程）上，`GET /api/auth/status` 为未初始化；紧接着的 setup 返回 `code:0` 和 token；再次查询 `initialized` 为 true。响应里的 token 没有写入本仓库。
