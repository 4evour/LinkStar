# [LS-06][高] 非法 Webhook 代理地址导致进程 panic

严重程度：高

建议标签：`bug`

相关报告：[LinkStar 审查报告](../LinkStar-audit-report.md) 第 LS-06 节。

## 现象

Webhook 的代理字段不是合法 URL 时，`Send` 对空的 `*http.Client` 解引用，发生空指针 panic。调度器在独立 goroutine 里调用它，没有 `recover`。Go 里未捕获的 panic 会让整个进程退出，而不是只让这一次 Webhook 失败。

## 定位

- `modules/webhook/sender.go`：`Send` 第 35–38 行。`client, err := buildClient(cfg.Proxy)` 之后没有判断 `err`，直接进入 `sendOnce`
- `modules/stun/scheduler.go`：`sendServiceWebhook` 第 678–679 行，`go func() { webhook.Send(...) }`

## 根因

`buildClient` 在 `url.Parse("://bad-proxy")` 失败时返回 `nil, err`。`Send` 丢掉这个错误。`sendOnce` 调用 `client.Do`。

## 稳定复现步骤

1. 调用  
   `webhook.Send(WebhookConfig{URL: "http://127.0.0.1:1/", Method: "GET", Proxy: "://bad-proxy"}, nil)`。
2. 观察 panic。审查里用 `recover` 接住后打印的是  
   `runtime error: invalid memory address or nil pointer dereference`。
3. 产品路径：已登录的管理端把某条 STUN 服务的 Webhook 代理填成同样的非法 URL 并保存，等该服务进入会发 Webhook 的状态。生产调用在第 678 行，没有 `recover`。

## 预期 vs 实际

预期：`Send` 返回「代理地址无效」，进程继续跑。

实际：`Send` 内部空指针 panic。测试里的 `recover` 能接住，说明 panic 出在 `Send`，不是测试自己。

## 建议修复方向

`buildClient` 的错误直接返回。再检查 scheme 只能是 `http` 或 `https`。调度器里的 `recover` 只作最后一道，不能代替返回错误。

## 证据摘要

临时测试输出：`recover=runtime error: invalid memory address or nil pointer dereference`，随后 `FAIL: TestAuditSendPanicsOnBadProxy`。该测试已删除，业务代码未改。
